# AI Event Planning & Engagement System

A Streamlit event management app combining a real ML attendance model, LLM-generated marketing copy (with a graceful offline fallback), lexicon-based sentiment analysis, and a small recommendation engine — built solo, end to end, from problem definition to a deployed, usable release.

**Live demo:** https://ai-event-planner-mxwjx5nzwrbfh3c8vbywjm.streamlit.app/

---

## The problem

Event organizers commit budget and staffing based on an *expected* headcount, but rarely have a data-backed way to sanity-check that number, and post-event feedback tends to sit in inboxes instead of feeding back into the next event's planning. This app tries to close that loop: predict attendance before the event, generate the marketing/planning work around it, then analyze feedback afterward and roll it back into recommendations for next time.

## Features

| Feature | What it actually does |
|---|---|
| **Attendance Predictor** | Random Forest regression trained on event attributes (type, day, time, location, promotion channel, budget, expected audience). R² = 0.83 on held-out data — see [Methodology](#attendance-model-methodology) below for what that number does and doesn't mean. |
| **Marketing Generator** | Calls OpenAI (`gpt-4o-mini` by default) to write email/Instagram/LinkedIn/reminder/thank-you copy for an event. **Falls back to a deterministic template** if no API key is configured or the call fails, so the app stays usable either way — the UI tells you which mode produced the output. |
| **AI Event Planner** | Rule-based strategy/checklist generator (event logistics, risk mitigation, engagement ideas, follow-up plan). No model call — deterministic and free to run. Named for consistency with the rest of the app, but worth being upfront that this one isn't ML/LLM-based. |
| **Feedback Analyzer** | Sentiment scoring via TextBlob (lexicon-based polarity, not a trained classifier) — good enough for a quick positive/neutral/negative read, not a substitute for reading the actual feedback. |
| **Analytics Dashboard** | Plotly charts over historical event data — attendance by type, promotion effectiveness, budget vs. turnout, etc. |
| **Recommendations** | Groups historical events by *turnout rate* (actual ÷ expected attendance, not raw attendance — see note below) to surface the best-performing event type, day, time, location, and promotion channel. |
| **Event History** | Persisted to Postgres (Supabase) when configured; falls back to local SQLite otherwise. The UI shows which backend is active. |

## What's real ML/AI here, and what isn't

Being direct about this because "AI-powered" gets used loosely and I'd rather the README hold up to a technical read than oversell it:

- **Real, trained ML**: the attendance predictor (Random Forest, scikit-learn).
- **Real LLM calls**: the Marketing Generator, when an API key with quota is configured.
- **Rule-based, not AI**: the Event Planner strategy generator and the Recommendation engine are both deterministic logic over structured data — useful, but not models.
- **Simple NLP, not deep learning**: the Feedback Analyzer uses TextBlob's lexicon-based polarity score.

## Attendance model methodology

The training data (`data/event_data.csv`) is **synthetic**, generated by `src/generate_dataset.py`. Each event's `actual_attendance` is `expected_audience` scaled by hand-picked multiplicative effects for event type, day, time, location, promotion channel, and budget, plus noise — the exact effect sizes are documented in that script's docstring.

That matters for how to read the R²: because the effects are hand-picked rather than fit from real event outcomes, **this demonstrates the ML pipeline** (feature engineering, train/test split, baseline comparison, evaluation) rather than a validated real-world predictor. To make sure the model was learning real structure and not just memorizing one dominant feature, I checked it against two baselines on the same test set:

| Model | R² |
|---|---|
| Naive (predict = expected_audience) | 0.597 |
| Linear regression | 0.734 |
| **Random Forest (this model)** | **0.830** |

The model clearly beats both, and feature importance is spread across all seven inputs rather than concentrated in one. An earlier version of this model also used `feedback_score` as an input — that was a genuine bug, not just a modeling choice: feedback is collected *after* an event, so an organizer predicting attendance beforehand can't possibly know it. It's now generated as a downstream *outcome* of attendance and excluded from the model's inputs. See `notebooks/attendance_prediction.ipynb` for the full walkthrough.

Swapping in a real historical event dataset with the same column schema would let this same pipeline produce genuinely predictive (not just internally consistent) results.

## Tech stack

- **Frontend:** Streamlit
- **Backend:** Python, PostgreSQL (Supabase) with local SQLite fallback
- **ML:** scikit-learn (Random Forest, Linear Regression baseline)
- **AI:** OpenAI API (`gpt-4o-mini`), with template fallback
- **NLP:** TextBlob (lexicon-based sentiment)
- **Visualization:** Plotly, Pandas
- **Deployment:** Streamlit Cloud

## Project architecture

```
Streamlit UI (app/main.py)
    ├── Attendance Predictor  → scikit-learn model (models/attendance_model.pkl)
    ├── Marketing Generator   → OpenAI API, falls back to template
    ├── AI Event Planner      → rule-based generator (no external call)
    ├── Feedback Analyzer     → TextBlob sentiment
    ├── Analytics Dashboard   → Plotly over data/event_data.csv
    ├── Recommendations       → turnout-rate groupby over historical data
    └── Event History         → Postgres (Supabase) or local SQLite fallback
```

## Setup

```bash
git clone https://github.com/OmkarK23/ai-event-planner.git
cd ai-event-planner
python3 -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### Optional: real AI-generated marketing copy

Without this, the Marketing Generator runs the rule-based template instead — the app works either way.

```bash
export OPENAI_API_KEY="sk-..."
```

Requires an OpenAI account with available billing quota (a ChatGPT subscription does **not** include API credit — they're billed separately).

### Optional: persistent Event History across restarts

Without this, Event History uses local SQLite, which works fine locally but resets on Streamlit Cloud redeploys.

1. Create a free project at [supabase.com](https://supabase.com).
2. Get your connection string: **Connect → Session pooler**.
3. Set it:
   ```bash
   export SUPABASE_DB_URL="postgresql://postgres.xxxx:yourpassword@aws-0-region.pooler.supabase.com:5432/postgres"
   ```

### Run

```bash
streamlit run app/main.py
```

For Streamlit Cloud deployment, add `OPENAI_API_KEY` and `SUPABASE_DB_URL` under **App settings → Secrets** rather than a local `.env` file — never commit either to the repo.

## Known limitations

- Attendance model is trained on synthetic data (see Methodology above) — treat predictions as a pipeline demo, not a forecast.
- Marketing Generator's "AI" mode requires a funded OpenAI account; without one, it silently (but visibly, via a UI message) runs the template fallback.
- Feedback Analyzer's sentiment scoring is lexicon-based and will miss sarcasm, negation, and domain-specific phrasing that a trained classifier would catch.
